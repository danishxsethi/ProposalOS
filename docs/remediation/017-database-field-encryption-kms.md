## Encryption Policy

To maximize security while retaining performance and system maintainability, Proposal Engine OS adheres to a strict multi-tier data protection policy:

### 1. One-Way Hashing (Verification-Only Fields)

- **Applicability**: API keys, session tokens, verification/magic links, and user password credentials that only require validation.
- **Strategy**: One-way secure cryptographic hashing (bcrypt/Argon2 for passwords, SHA-256 for API keys and lookup tokens). This prevents the recovery of plaintext even if the database is fully compromised, making them immune to decryption failures.

### 2. Two-Way Authenticated Encryption (Plaintext Recovery Fields)

- **Applicability**: OAuth refresh tokens, access tokens, integration secrets, outbound provider keys, and SMTP credentials.
- **Strategy**: Reversible application-level authenticated encryption using **AES-256-GCM** via the Node.js native `crypto` module.

### 3. Envelope Encryption Format

Every encrypted secret is represented as a serialized JSON string representing an `EncryptedFieldEnvelope`:

```json
{
  "v": 1,
  "alg": "aes-256-gcm",
  "kid": "local-v1",
  "iv": "3a7c8db3...",
  "tag": "df9a12c4...",
  "ciphertext": "e58b3f..."
}
```

- **v**: Format schema version for backwards compatibility.
- **alg**: Cryptographic algorithm identifier (`aes-256-gcm`).
- **kid**: Key Identifier specifying which key from the keyring was used for encryption (rotation-ready).
- **iv**: Unique 12-byte random initialization vector/nonce (never reused across encryptions).
- **tag**: 16-byte authenticated encryption tag generated by AES-256-GCM to prevent ciphertext tampering.
- **ciphertext**: Hex-encoded encrypted data.

### 4. Cryptographic Binding (AAD)

To prevent **ciphertext swapping attacks** (e.g., an attacker copying ciphertext from a low-privilege record and writing it into a high-privilege record to force the system to decrypt it), the encryption and decryption processes bind an **Associated Authenticated Data (AAD)** context:

```typescript
export interface EncryptionContext {
  model: string; // e.g., 'Account'
  field: string; // e.g., 'access_token'
  recordId: string; // e.g., 'google:12345' (provider:providerAccountId)
}
```

The context is sorted alphabetically, serialized canonically, and passed into `cipher.setAAD(aad)`. Decryption will fail immediately if any part of the model, field, or record ID has been altered.

### 5. Fail-Closed Behavior

In production, if the environment encryption keys are missing or invalid, the system throws an explicit, hard startup exception rather than falling back to weak defaults or plaintexts.

## Key Management Design

Centralized keyring management is implemented at `lib/security/encryption/keyring.ts`.

### 1. KMS-Ready Interface

The system isolates key-retrieval behind a clean interface:

```typescript
export interface KeyProvider {
  getPrimaryKey(): Promise<{ kid: string; key: Buffer }>;
  getKey(kid: string): Promise<Buffer>;
}
```

This is fully prepared to swap out the environment provider (`EnvKeyProvider`) for a production cloud provider (such as GCP Key Management Service or AWS KMS) without changing any downstream encryption code.

### 2. Environment Keyring Implementation

- `FIELD_ENCRYPTION_PRIMARY_KEY`: Standard Base64-encoded 32-byte (256-bit) primary key.
- `FIELD_ENCRYPTION_KEY_ID`: Identifier for the current primary key (e.g. `prod-v1`).
- `FIELD_ENCRYPTION_PREVIOUS_KEYS`: JSON mapping of previous `kid` values to Base64 keys to support key rotation without service interruption. Legacy records containing prior key identifiers are decrypted using the legacy key matching their `kid`.

## Backfill / Migration Plan

A standalone utility at `scripts/encryption/backfill-encrypted-fields.ts` facilitates dry-runs and safe migrations of existing plaintexts in dev, staging, or production:

1. **Idempotency**: The script checks if fields are already encrypted using `isEncryptedField(value)`. It only processes fields that sit in plaintext.
2. **Batch Processing**: Database records are loaded and updated in batches (default size 50) using transactional boundaries to ensure high-performance and safety.
3. **Dry-Run Mode**: Defaults to `--dry-run` where it prints record counts and target operations without performing database writes.
4. **Safety Verification**: Refuses to run against non-development databases unless the `--apply` flag is explicitly passed. Values are never printed to output.

---

## Redaction Review

Plaintext secrets are systematically scrubbed from all diagnostic output:

1. **Log Scrubber (`lib/logger.ts`)**: Recursive scanner matches sensitive keys (e.g., `access_token`, `refresh_token`, `secret`, `password`) and intercepts serialized `EncryptedFieldEnvelope` formats, replacing them with the unified literal `[ENCRYPTED]`.
2. **Audit Trail Payload Scrubber (`lib/observability/auditTrail.ts`)**: Audit payloads undergo automatic property recursion, censoring any sensitive values to ensure raw plaintexts never escape to persistent log files.

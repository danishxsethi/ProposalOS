# ProposalOS production infrastructure (AWS)

This separate Terraform root targets AWS account 410432886960 in us-east-2 and uses a dedicated S3 state key, production secrets namespace, VPC CIDR, S3 data bucket, ECR repositories, and ECS cluster. It is derived from the accepted staging stack and is configured for the verified production hostname claraud.com.

**Live status (2026-10-06):** API and web are each 1/1 on immutable image tag `production-20261006-1`; ALB targets are healthy, `/api/health` is healthy, and the domain resolves to AWS. LLM requests are configured for Bedrock Nova profiles. Google Places enrichment uses SerpApi Google Maps, PageSpeed uses local Lighthouse, and Google Custom Search uses SerpApi; these changes remove runtime dependence on Google API keys for those features. Google Fonts and external Google OAuth remain third-party integrations, not GCP-hosted runtime services. GCP project billing is disabled, while its runtime and backups remain retained for rollback.

**GCS object transfer (2026-10-06):** one current audit-snapshot object, three log objects, and one Terraform state object were copied from GCP and verified against source size/MD5 and destination SHA-256; source generations and checksums are retained as S3 object metadata. The app objects are in the matching S3 prefixes, except GCP logs are isolated under `logs/gcp-archive/` to avoid collisions with existing AWS build artifacts. The GCP state object is in a separate prefix in the encrypted/versioned Terraform state bucket and is archival only. No source objects were deleted. The GCP project was briefly linked to its authorized billing account for the copy, then unlinked again. Database storage-reference reconciliation and app delivery qualification remain open.

The production database uses PostgreSQL `db.t4g.medium` with 50 GiB and Multi-AZ; seven-day automated backups and deletion protection remain enabled. The final write-paused export was imported and the AWS database is serving production. Terraform defaults keep production API/web services, public ingress, and audit dispatch enabled after the verified cutover. Set those flags false only for an intentional shutdown. The one-shot importer remains disabled by default; it accepts only a unique final write-paused export and publishes `DATABASE_URL` after restore and least-privilege grants succeed.

This root includes authenticated API self-dispatch plus an enabled EventBridge Scheduler fallback that starts a short-lived Fargate task every five minutes to poll the PostgreSQL audit queue. No always-on worker task is required. The Oct 4 inventory found two GCP production worker services and four production Cloud Run batch-job resources. They share the `proposal-engine:latest` image; the deployed job templates set `JOB_MODE` but specify no command or args, and the candidate image source has no matching runtime handler. Cloud Run returned no latest-execution metadata for those jobs. The checked-in `cron.yaml` documents intended schedules, but Cloud Scheduler and Cloud Tasks APIs were disabled in the GCP project, so the live schedule set remains unverified. Do not port the four inert-looking batch templates as working jobs; reconcile source provenance and actual use before enabling any additional scheduled endpoint.

The schedule inventory adds a separate parity gate: `cron.yaml` declares 13 schedules, 11 without an explicit disabled flag and two marked disabled. The production AWS root currently runs only the audit queue sweep at five-minute intervals; `cron.yaml` specifies one minute for that endpoint. The other ten intended endpoints have no AWS schedules in this root. GCP returned no Cloud Scheduler/Cloud Tasks jobs, so the checked-in schedule file is not evidence that those tasks were active. Confirm which endpoints have real external triggers and are still required before adding schedules; preserve their secret authentication and avoid enabling email, billing, or tenant-processing side effects by assumption.

The 30-day Cloud Run request-log query returned no `/api/cron/*` or `/api/worker/audit-job` requests, and no request logs for either separate production audit/outreach worker service. Along with the disabled GCP Scheduler/Tasks APIs and absent job executions, this is evidence those HTTP schedules/workers were not exercised in that 30-day window; it does not rule out older activity or triggers outside the retained logs.

The legacy `scripts/setup-cron-jobs.sh` is not a safe schedule source: it hard-codes project ID `proposal` instead of production project `proposal-487522`, sends POST for every route although seven intended routes expose only GET, and includes a hard-coded `CRON_SECRET` fallback. Do not run it. No credential value was copied into this note. Cloud Scheduler returned no live jobs, but check whether the fallback was ever used outside this project and rotate it if so.

This root is applied and a fresh Terraform plan previously reported no changes before the 2026-10-06 application release. The production API/web services and audit queue dispatch path are live, and GCP project `proposal-487522` is unlinked from billing. The release provenance manifest records a dirty source worktree, so it does not establish a clean Git commit-to-image build. GCP Cloud SQL is stopped with its latest successful production backup retained; do not delete the database or backup until AWS database contents, object references, and recovery are verified. The 2026-10-06 health checks prove service and dependency availability, not complete customer-flow acceptance or a successful database restore.

Before declaring the migration complete, verify GCP-to-S3 object counts/checksums and metadata, production database totals and restore/PITR, application flows, the full required schedule/worker set, and CDN/WAF/DNSSEC/security parity. Only the audit queue sweep is currently represented in AWS schedules; the other checked-in cron endpoints and inert-looking GCP batch templates remain unqualified. Keep GCP resources available for rollback until these acceptance gates pass.

The current GCP production `DATABASE_URL` secret resolves to `proposal_engine`, confirming the populated database identified by the metadata-only export review. The production source environment also confirms Stripe live mode, a live publishable key, the Starter price/product IDs, the sender address, and a default tenant ID. The AWS task definitions and image build preserve those settings. Their nonsecret configuration belongs in an ignored production `.tfvars.json` file, not in Git. AWS has its own production-only `WORKER_SECRET`; `GOOGLE_AI_API_KEY` was omitted because application LLM traffic now uses Bedrock.

All 15 production runtime secrets now have current versions in AWS Secrets Manager. Fourteen GCP production values were transferred and a fresh production-only WORKER_SECRET was generated. Secret values were not printed and temporary transfer files were removed. GOOGLE_AI_API_KEY was not copied because model requests use Bedrock; AWS creates its own DATABASE_URL and REDIS_URL.
